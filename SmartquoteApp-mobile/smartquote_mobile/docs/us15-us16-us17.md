# US15, US16 y US17 en Flutter

Se mantiene el tema Material 3, Roboto, tarjetas y colores actuales. Los repositorios HTTP usan el mismo cliente autenticado y los roles publicados por IAM. No se incluyen semillas, tokens manuales ni datos simulados en producción.

## US15 — Aclaraciones

1. Analista: abrir una solicitud activa. Cada requisito tiene **Solicitar aclaración**; el ítem y requisito quedan vinculados, y el destinatario es el especialista solicitante, como exige la API actual.
2. Registrar la pregunta. El servidor conserva autor y fecha. Consultar la pestaña **Aclaraciones** de la solicitud.
3. Producción: menú **Aclaraciones**, donde se consulta la bandeja propia. Marcar lectura es opcional; después se recarga para usar la versión vigente. **Responder** conserva interpretación, responsable y fecha sin modificar el requisito.
4. Si la respuesta exige un cambio: **Revisar especificación**, editar nombre/operador/valor/unidad y justificar. Un requisito obligatorio no se puede desmarcar. **Confirmar cambio** envía ambas versiones esperadas; no se reintenta automáticamente una revisión obsoleta.
5. El historial muestra valores anterior/nuevo, autor, fecha y motivo. Se recarga la solicitud tras revisar. El backend invalida las simulaciones anteriores afectadas: configurar una nueva versión de criterios y volver a evaluar antes de aprobar.

Un conflicto `409`, prohibición `403` o regla `422` queda visible; actualizar permite revisar el estado del servidor. La app no sustituye una versión sin conocimiento del usuario ni convierte una respuesta en autorización de compra.

## US16 — Recurrencias

1. Producción: menú **Programaciones → Nueva programación**. Registrar primera fecha de generación, intervalo (1–3650 días), días hasta fecha requerida (0–3650), prioridad, ítems y requisitos. Zona: `America/Lima`.
2. Consultar programación, responsable, plantilla, siguiente fecha y ocurrencias. La generación corresponde al trabajador del backend, no al celular; el servidor debe permanecer activo.
3. Abrir la solicitud de una ocurrencia o usar el filtro **Borrador por revisar** en Solicitudes. **Editar borrador** recupera los valores actuales, permite modificarlos y guarda con su versión original. No envía la solicitud.
4. **Confirmar y enviar solicitud** pide confirmación y llama a `/submit`. El servidor verifica fecha y reglas; una fecha vencida requiere edición antes del envío.
5. Actualizar las programaciones solo consulta las ocurrencias existentes: no se genera otra solicitud ni se reemplazan ediciones. **Suspender programación** usa su propia versión y conserva las solicitudes e historial anteriores.

Los borradores son privados del especialista. No hay procesamiento automático móvil ni órdenes de compra creadas por la programación.

## US17 — Vencimientos

1. Analista: menú **Vencimientos**. La bandeja muestra proveedor, solicitud, fecha de vencimiento, anticipación y lectura, con filtro de no leídas y paginación.
2. **Marcar leída** confirma el aviso existente. Actualizar recupera los mismos identificadores del servidor; el cliente no crea alertas ni reinicia su lectura.
3. **Ver solicitud** abre su contexto. **Ver vigencia actual** consulta la cotización y muestra si el backend la declara vencida/no vigente. La lista de cotizaciones también distingue las ofertas vencidas.
4. El historial puede contener ofertas vencidas o solicitudes cerradas: no se borra ni se presenta como prueba de vigencia actual. Leer un aviso no amplía condiciones ni habilita una aprobación. El backend sigue siendo la autoridad en vigencia y aprobación.

Para recibir alertas se necesita una solicitud activa **con analista asignado** y una oferta verificada próxima a vencer. La asignación y el trabajador de alertas pertenecen al backend; estas historias no añaden una asignación automática.

## Entorno y verificación

- El backend desplegado debe incluir las migraciones y rutas de US15–US17. Un backend antiguo puede devolver `404`; la app no simula una respuesta alternativa.
- Las cuentas que actúan sobre aclaraciones y programaciones deben existir activas en IAM, además de tener el rol correspondiente.
- Pruebas nuevas: `test/request_workflows_test.dart`. Cubren contratos, contexto y versiones, respuesta/revisión separadas, errores, borradores sin autoenvío, repetición de consultas, suspensión y lectura de alertas; incluyen pruebas de widgets.
- Ejecutar `flutter analyze`, `flutter test` y `flutter build web --debug`. Las pruebas de contratos/widgets usan dobles de la API: no sustituyen la validación integrada con PostgreSQL ni una prueba en APK/dispositivo.
- La prueba `live_backend_test.dart` es optativa y requiere las variables `SMARTQUOTE_SMOKE_API`, `SMARTQUOTE_SMOKE_EMAIL` y `SMARTQUOTE_SMOKE_PASSWORD`. No guardar credenciales en el repositorio.
